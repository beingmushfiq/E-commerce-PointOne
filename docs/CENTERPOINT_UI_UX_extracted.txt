01. Executive design brief
CENTERPOINT is a modular commerce platform intended to serve independent merchants and growing businesses through two deployment modes: standalone commercial software and a centrally operated multi-tenant SaaS edition. Its UI must make that architecture understandable without exposing technical complexity to customers or merchants.
The product is composed of three experiences with different primary jobs:
EXPERIENCE
PRIMARY USER
PRIMARY JOB
DESIGN CHARACTER
Storefront
Shopper / customer
Discover, evaluate, purchase and track products.
Brand-led, expressive, fast, reassuring.
Store Studio
Merchant owner and store team
Operate commerce, inventory, finance, marketing and content.
Productive, information-rich, predictable.
Master Control
CENTERPOINT platform personnel
Operate tenants, subscriptions, platform services, security and support.
Authoritative, controlled, observability-led.
Design outcomes
Clear separation between customer, tenant-staff and platform-operator workflows.
High-quality multi-industry storefront themes, rather than one generic storefront layout.
One Store Studio application with a full-screen page-building workspace—not a separate CMS product.
Role-based Master Control access from the first release, with least-privilege permissions and traceable privileged actions.
Consistent visual language, navigation logic, component behavior and state handling across the ecosystem.
Honest, data-backed interfaces: no fabricated KPIs, simulated health indicators or decorative actions presented as operational features.
Non-goals
This document does not prescribe a new backend architecture or replace the existing Laravel domain model.
This document does not imply that all target modules are already implemented or production-verified.
The Master Control Panel must not become the place where tenant-specific daily store operations happen.
The CMS must not allow tenant-authored code to execute in the privileged Studio origin.

03. Product experience architecture
The experience architecture should reflect the platform’s trust boundaries and the real mental models of its users. Storefront, Studio and Master Control are separate route-level applications within the broader platform, even if they share a frontend deployment or component package.

Other tenants’ business records or SaaS-wide infrastructure controls.
Visual CMS workspace

STANDALONE EDITION RULE
Standalone installations still use Storefront and Store Studio. SaaS Master Control routes and central-tenant workflows are unavailable or hidden in standalone mode; core commerce must not depend on Master Control to function.

Layout and component rules
Use a consistent spacing scale based on 4px increments; favor 8px and 12px rhythm for dense operational layouts.
Use 8–12px corner radii for operational components and 12–18px for large cards and surfaces. Avoid making every control pill-shaped.
Use a clear 12-column desktop grid with a comfortable maximum content width; the storefront may use wider full-bleed editorial sections.
Use consistent icon sizing and stroke weight. Icons supplement labels and should not replace critical navigation text.
Data tables should prioritize scannability: sticky headers where useful, aligned numeric columns, compact row density controls and clear filters.
Use elevation only to clarify layering: dropdowns, menus, dialogs and floating inspectors. Do not cover every card in shadows.
Keep tenant brand tokens separate from platform-admin tokens. Tenant theme changes must never recolor the Master Control security or billing interface.

AUDIENCE: VISITORS, SHOPPERS AND RETURNING CUSTOMERS
The storefront is the merchant’s public brand experience. It should communicate product value quickly, remove friction from shopping and feel appropriate to the merchant’s industry. The same commerce engine can power distinct storefront themes without making every store look alike.
Storefront global shell
Announcement bar: optional delivery promotion, campaign message or service notice; dismissible where configured.
Header: brand mark, primary navigation, search, locale/currency where supported, account, wishlist and cart.

Footer: customer service, policies, contact details, social links, payment/shipping trust marks and newsletter where enabled.
Global search overlay: predictive results, categories, products and recent searches; keyboard and screen-reader friendly.

Product detail and checkout rules
Price, discount, tax, shipping and totals must be sourced from authoritative server calculations.
Stock availability must distinguish in stock, low stock (only where the business permits disclosure), unavailable and backorder/preorder states.
Variants must be represented as a clear matrix or selectors; the selected SKU and price must be unambiguous.
Payment gateway options should appear only when configured and available for the tenant, currency and order context.
Bangladesh-ready fields should support local phone formats, district/city/area data and clear delivery notes; international fields remain configurable.
Never claim a payment is successful based only on a client-side return URL. Show pending verification until the server confirms the transaction.

Editor interaction model
Selecting a section in the canvas synchronizes selection in the layer tree and inspector.
Adding a component opens a searchable library grouped by content, commerce, navigation, trust and layout.
Drag-and-drop must show a clear insertion target and preserve predictable focus for keyboard users.
Device switching previews breakpoints; it must not silently change the page’s saved breakpoint-specific settings.
Undo and redo operate on the editor session with clear limits; autosave and revision history remain server-backed.
Preview opens a customer-facing draft preview in a safe, isolated context; it must not publish the draft.

09. Role-based access and governance
Role-based access should be designed now, not added after the navigation and screens have been built. The interface must be driven by backend-authoritative permissions. Hiding a button is not authorization.

Permission dimensions
DIMENSION
EXAMPLES / EXPECTATION
Resource
Products, orders, stock, journals, pages, staff, tenant records, platform settings.
Action
View, create, edit, delete/archive, approve, publish, export, refund, reverse, provision, suspend, impersonate/support-access.
Scope
Own records, assigned warehouse, selected channel, all records in one tenant, selected tenants or platform-wide.
Sensitivity
Normal, financial, personal data, credentials/secrets, destructive, privileged support or security-critical.
Context
Active tenant, environment, current workflow state, approval state and time-limited access grant.
Access-control UX requirements
Navigation, page actions, bulk actions, exports and record fields must be permission-aware.
Permission-denied states should explain that access is restricted and identify the appropriate administrator path without exposing protected data.
Role assignment should show a readable permission summary, not only a role name.
High-risk permissions (refund, journal posting/reversal, publish, staff administration, tenant suspension, support access and platform-wide configuration) should be separately visible.
Where dual approval is required by business policy, the requester cannot approve their own action.
All privileged actions create an audit record with actor, role, action, target, timestamp, result, reason and correlation ID.
Backend policy is authoritative. The frontend must not infer access from a local role label or cached menu alone.

11. Accessibility, performance and trust
Accessibility baseline
WCAG 2.2 AA should be the target for all core user journeys.
All interactive components support keyboard navigation and visible focus; focus order follows the visual hierarchy.
Images provide useful alt text or are correctly marked decorative. CMS validation flags missing meaningful alt text.
Form fields have persistent labels, instructions, required state, inline errors and summary where needed.
Charts include concise text summaries and accessible data alternatives; color is never the only indicator.
Use semantic headings, landmarks, table headers and accessible names for icon-only controls.
Respect reduced-motion preferences and do not use flashing or motion that creates avoidable discomfort.
Ensure tenant theme customizations cannot reduce contrast below approved thresholds for core interface elements.
Performance expectations
AREA

Optimize imagery, responsive sources, lazy-load below-the-fold media and avoid blocking the first meaningful content.
Studio / MCP
Use server pagination, filtering and sorting for large datasets; virtualize exceptionally long lists only where justified.

Keep route transitions responsive; load module bundles on demand where it improves user experience.

For platform support access, show an unmistakable support-access banner and preserve a detailed audit trail.
